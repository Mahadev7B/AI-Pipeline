#9 — Milestone 2B4: Founder authentication mechanism selection
2026-08-30
Problem: The session-token mechanism (Milestone 2B1+) proves a request came from a page this server process rendered, but does not prove a human, specifically the Founder, sent it -- risks.id=2, open since Phase 1. This milestone had to close that gap for the current local/internal, solo-Founder, loopback-only Control Center deployment, without adding a paid identity provider, external cloud infrastructure, or any third-party dependency, unless the threat model genuinely required it (it did not).
Decision: Implemented ops/control-center/founder_auth.py (scrypt N=2**17/r=8/p=1, 16+ character passphrase floor, atomic 0600 credential file outside git) plus a Founder-session cookie (HttpOnly, SameSite=Strict, 30-minute idle / 12-hour absolute timeout, in-memory only) gating all 9 write/auth routes and every GET read at the same centralized location the pre-existing CSRF SESSION_TOKEN check already occupied -- kept, not replaced. Fully serialized login verification closes both the stated brute-force cap and a concurrent-scrypt memory-exhaustion DoS, independently verified under a 60-simultaneous and a 45,820-request sustained flood (Code Review, QA, and Security's post-implementation adversarial review each PASS).
Reason: Smallest credible mechanism for the actual deployment model: a solo Founder's own local internal tool, not a public SaaS product. Answers 'does the entity submitting this request know a secret only the Founder was ever told' with a real, independently-reproduced technical guarantee, without adding infrastructure the threat model does not justify.
Tradeoffs: Does not and structurally cannot defend against an agent with Bash tool access sharing the Founder's own OS-user filesystem/process principal (risks.id=3, explicitly out of scope this milestone) -- such an agent can read/overwrite the credential file directly or PTRACE_ATTACH the running server. Also disclosed: the shared, non-identity-scoped lockout can itself be flooded to deny the Founder's own genuine logins (Red Team finding F1) -- no cheap in-scope fix exists without touching risks.id=3. Neither gap is hidden; risks.id=2 moves to mitigated, not resolved.

#7 — TASK-011 Milestone 2B3B round 2: compound-failure reservation leak in add_meeting_participant() accepted as a known, non-blocking gap (no reconciliation sweep built)
2026-08-30
Problem: gather_requested_position()'s reservation-then-invoke pattern (opsdb.add_meeting_participant() reserves a manually-requested participant's slot before invoking them) correctly closes the primary TOCTOU race (QA id=15 defect 2) and its own two exception windows A/B (Code Review id=17, fixed at 6ee5503) via a try/finally-guaranteed _release_reservation() call. But one narrower path remains open: if the cleanup opsdb.end_run(...,'failed') call AND _release_reservation()'s own opsdb.remove_meeting_participant() call both raise sqlite3.OperationalError in sequence on the same connection (ordinary write contention, not a process kill -- Code Review id=19/20 corrected the record on this after 6ee5503's own disclosure undersold it as 'SIGKILL only'), the reservation leaks permanently: a phantom 'requested' participant with no message and no open agent_runs row, occupying a MAX_MEETING_PARTICIPANTS cap slot with no automated path back to a real position or removal short of manual DB surgery. No reconciliation sweep for orphaned participant reservations exists (unlike agent_runs orphans, which DO have one via reconcile_orphaned_runs() and the 3 ACTIVITY_LIKE patterns).
Decision: (b) -- accepted as a known, disclosed, non-blocking gap for this round. Independently re-verified by CTO post-implementation conformance (this review): QA's own 8-real-concurrent-thread load test (id=21) produced zero sqlite3.OperationalError at this project's realistic concurrency ceiling (MAX_CONCURRENT_INVOCATIONS=3), and Security's review (id=22) found that anyone able to force the double-fault already holds the SESSION_TOKEN and has a strictly easier way to deny participant slots (call request-perspective 6 times legitimately). Not a privilege escalation, not a materially worse DoS than the existing trust model already grants a token holder -- an availability/integrity nuisance, not a security-severity gap.
Reason: Recorded as its own decision (not left only in agent_activity log entries id=17/18/19/20/21/22, five gates deep in a long fix chain) so a future round's CTO/Red Team/Security can find this accepted gap without re-deriving it, the same durability the participant-cap revision (an earlier decision this same round) already gets. This is exactly the kind of accumulated-context item this gate exists to surface rather than silently pass over.
Tradeoffs: If this gap is ever actually triggered in practice (requires sustained above-normal write-lock contention hitting two specific sequential writes within one failed invocation's cleanup path), a phantom participant permanently occupies a cap slot until manual DB surgery -- no user-facing crash, no data corruption elsewhere, no privilege escalation. A future round should build the reconciliation sweep (option a) before this feature sees production-scale concurrent load meaningfully higher than this milestone's own MAX_CONCURRENT_INVOCATIONS=3 ceiling, since QA's own load test only validated the gap's non-reachability at THIS ceiling, not at a higher one.
