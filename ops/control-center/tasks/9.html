• Note on process: performed directly rather than via a spawned code-review subagent (the Agent dispatch tool became unavailable partway through this milestone, session-level change) -- same rigor, same empirical-testing discipline, disclosed here rather than silently changing how this gate is staffed.
• One real bug found and fixed: _handle_ask only called opsdb.end_run() on the two EXPECTED outcomes (invoke_agent success/failure) -- an unhandled exception anywhere between a successful start_ask_agent_run() and those two branches (e.g. a send_message() failure, a bug in _build_transcript) would leave that agent_runs row open (ended_at IS NULL) forever, silently blocking every future Ask-Agent request to that same agent until the next server restart's reconciliation pass. This directly violates the milestone's own acceptance bar ('failures... in one invocation do not corrupt or block another') exactly as surely as the race the milestone's headline fix closes. Fixed by wrapping the post-run-creation logic in its own try/except that unconditionally ends the run as 'failed' before re-raising to the outer handler. Verified live end to end with a real running server: injected a real in-process exception via a monkeypatched send_message call after a genuine model invocation had already completed, confirmed a clean 500 (no crash, no hang), confirmed the run correctly shows status='failed' with ended_at set (not orphaned), and confirmed a subsequent real request to the SAME agent succeeds normally afterward (not blocked).
• Independently re-verified (not re-trusting Development's own claims): the outer try/except/finally structure correctly closes the connection on every exit path including returns from the nested exception handlers (Python's finally-on-return guarantee, confirmed by re-reading + the live tests all showing clean behavior with no leaks). No shared mutable state exists anywhere in layout.py/generate_agents.py/dbutil.py that threading would put at risk. Handler.timeout and the daemon_threads setting behave correctly per-instance under ThreadingHTTPServer. Startup reconciliation still runs strictly before serve_forever(), no race with request threads. Re-ran the real concurrent-different-agent test after the fix -- no regression (~4.5s wall time for two real overlapping invocations, both 303).
• Minor, accepted, not fixed: if opsdb.end_run() itself were to raise something other than LookupError/ValueError inside the new except-and-end-run block (e.g. a raw sqlite3.OperationalError from a genuinely broken connection), that secondary exception would propagate instead of the original one (Python exception chaining preserves both via __context__, but only the outer exception gets logged today). Judged disproportionate to add further nested handling for this already-last-resort, low-probability path.

• BLOCKING finding, fixed before Development proceeds: the proposed start_ask_agent_run() wraps BEGIN IMMEDIATE inside the same try/except that does ROLLBACK on failure -- reproduced empirically that if BEGIN IMMEDIATE itself fails (busy timeout), no transaction is open, and the subsequent ROLLBACK call raises a SECOND, masking OperationalError ('cannot rollback - no transaction is active') instead of the real 'database is locked' one. Fix: BEGIN IMMEDIATE must execute outside the rollback-guarded block; server.py must catch sqlite3.OperationalError from this call and handle it as a clean busy/retry signal, same as capacity_exceeded.

WAL-mode deferral affirmed, with QA required to watch for real lock-contention evidence to reopen it. BEGIN IMMEDIATE + dedicated function affirmed over a partial-unique-index alternative (avoids fragile schema tricks). Non-blocking semaphore acquire affirmed, conditional on Code Review verifying acquire/release wraps every exit path of invoke_agent().
