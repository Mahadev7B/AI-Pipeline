Red Team review · review_results #17
pass
2026-08-29T03:25:20.721Z
by red-team
• PASS with conditions. Core design (agent_runtime.py as a small, provider-neutral, dependency-free module; ASK_AGENT_ALLOWLIST enforced server-side only, never client-supplied; argv-list subprocess.run with shell=False, eliminating shell-injection surface regardless of message content; atomic-style validate-before-write sequence mirroring decide_approval(); additive-only schema migration; --no-session-persistence keeping messages/agent_runs the sole conversation store) correctly targets every hard requirement in the brief and is not overengineered. No simpler design was found that still satisfies 'browser never invokes Claude Code/shell/SQLite directly, server mediates every request, real queued->running->completed|failed lifecycle, one conversation store.'
• CONDITION (blocking, core safety claim #1): --tools "" alone is an unverified, narrower safety boundary than the CLI itself offers for exactly this scenario. Verified directly against the live 'claude --help' in this environment: the CLI ships a purpose-built --restricted flag whose documented behavior is materially broader than --tools "" -- it 'removes the built-in tools that run commands or code (Bash, PowerShell, REPL...) and WebFetch unless --tools names them, and ignores user, project and local settings files (managed settings and --settings still apply; add --strict-mcp-config to skip MCP servers too). Also confines file tools to working directories, refuses bypassPermissions, and lets only a person or the configured permission handler approve writes to settings/git/tool-config files.' None of that is claimed for --tools "" alone -- its own help text says only 'Specify the list of available tools from the built-in set,' which by its own wording leaves open whether MCP-server-provided tools (not part of the 'built-in set') are constrained by it at all, and says nothing about ignoring user/project/local settings files or refusing bypassPermissions. The proposal's empirical verification (asking cto to run ls -la / read a file) only exercised Read/Grep-class built-in tools -- it never tested WebFetch (a real network-exfiltration path for prompt-injected Founder text), any MCP-provided tool, or whether a stray user-level settings.json on the actual deployment machine (outside this repo's control) could reintroduce permission overrides. Given this milestone's own framing as 'the first time an LLM call happens unsupervised,' relying on the narrower-documented flag when a purpose-built stronger one exists is not adequate. REQUIRED: agent_runtime.py must pass --restricted (layered with --tools "" if useful) and --strict-mcp-config; Security must re-run adversarial verification explicitly covering WebFetch/WebSearch, any configured MCP server, and confirm no reachable user/project settings.json can reintroduce tool access, before this ships.
• CONDITION: subprocess hardening details are unspecified and should be pinned down before implementation, not improvised mid-build -- (a) kill the whole process group on TimeoutExpired (start_new_session=True + os.killpg), not just the direct child, in case the claude CLI spawns children before a runaway call is killed; (b) pass an explicit minimal env= rather than blindly inheriting the full parent environment, as further defense-in-depth given the 'unsupervised process' risk framing; (c) cap captured stdout size defensively (subprocess.run has no built-in cap).
• CONDITION: no size cap is proposed for the agent's stored RESPONSE text -- the 8KB cap only covers the Founder's inbound message. A pathological or adversarially-elicited long response bloats messages/agent_runs indefinitely and gets re-rendered on every subsequent page load with no bound. Add a symmetric cap (truncate-and-flag, or treat as runtime_error) before persisting the response.
• CONDITION: stored-XSS risk on the new conversation thread is not explicitly addressed in the proposal, and this is the first feature combining fully free-text Founder input with free-text, potentially prompt-injected model output, both persisted and re-rendered as live HTML on every load. The codebase's existing layout.e() (html.escape) convention, already applied to every DB-sourced string per the Milestone-1 rule, is the correct and sufficient fix, but the proposal's 'Files touched' list doesn't call it out for the new bubbles in build_agent_detail(). REQUIRED: Development must run both Founder and agent message bodies through e() exactly like every other field; QA/Security must add a seeded <script> payload test against both the Founder-submitted message and an adversarial agent response, mirroring the exact test Security already ran for 2B1 (review_results id=14).
• CONDITION (concurrency, question 4 in the proposal): the 'one open run per agent -> 409' analysis only reasons about a second request to the SAME agent racing the first. Because HTTPServer is strictly single-threaded and sequential, the real, larger cost is that ANY other request -- a different agent's Ask-Agent POST, or simply loading /overview.html, /pipeline.html, /agents.html, or the approvals inbox -- will silently hang in the OS accept queue (not get a clean response, not get a 409) for up to the full timeout_s (90s) while the server is synchronously blocked inside subprocess.run() for an unrelated agent. This is materially broader than the narrow same-agent scenario the proposal frames and asks Red Team about. May be an acceptable tradeoff for a single-Founder internal tool proving one vertical slice, but it must be explicitly disclosed (in this doc and/or SECURITY.md, the way every other tradeoff here is disclosed) rather than framed only as the narrower case, and the Founder/CTO should explicitly accept it. Also recommend lowering the default timeout well below 90s given the proposal's own measured real-world latency was ~3-13s.
• CONDITION: an orphaned 'open' agent_runs row (ended_at IS NULL) on server crash/restart permanently blocks all future requests to that agent, with no recovery path proposed. Because agent_runs rows in this synchronous, single-process design are inherently process-lifetime-scoped (no cross-process handoff of an in-flight subprocess is possible), any row left open at server startup cannot correspond to a still-running call. REQUIRED: add a startup reconciliation step that marks any pre-existing open agent_runs rows as failed (e.g. note='orphaned by server restart') before serving new requests, so a crash/restart doesn't permanently wedge that agent's chat.
• CONDITION (should-fix): reusing the identical 2B1 session token for this new, higher-blast-radius write route is architecturally consistent but was not re-justified for the escalated risk, and the proposal's 'Files touched' list omits ops/SECURITY.md. SECURITY.md's existing disclosure already states this same token does not prove Founder identity and that any local process able to read the served page -- 'including an agent invoked with Bash tool access, per the still-open Phase 1 risk (risks.id=3)' -- can forge the same POST. Verified against the live .claude/agents/*.md files: all five allowlisted agents (cto, qa, ceo, financial, project-manager) are normally configured WITH Bash tool access in their peacetime setup (cto also has Write/Edit) -- contrary to the proposal's framing of them as low-risk 'read-oriented' agents for this specific point, they are exactly the actors risks.id=3 already worries about.
