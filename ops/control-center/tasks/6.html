Rejected a cookie/startup-code login upgrade as a REQUIRED change for this milestone because it would itself be a session/login mechanism, which the Founder explicitly ruled out of scope here; flag it as a good candidate for the milestone that actually tackles Founder auth, not now.
• Q2 (concurrency): atomic UPDATE...WHERE is real and correct, but the proposal only reasons about concurrent HTTP requests (moot -- HTTPServer is single-threaded) and does not address the actual cross-process race: server.py's long-lived writable connection vs a concurrently-run opsdb.py CLI write (e.g. approval-decide or any task write) hitting the same file with no busy_timeout set anywhere in connect(). CONDITION: QA must test true cross-process concurrent writes (CLI process + running server, not just concurrent curl to the server), and Development must confirm/set an explicit timeout rather than rely on the sqlite3 module default.
• Beginner-mistake risk: decide_approval(conn, ...) must explicitly commit its own transaction (not rely on a 'with conn:' pattern sized for the CLI's short-lived connection). server.py will hold one long-lived connection across many requests; if decide_approval() only executes the UPDATE without an explicit commit, the browser response looks successful (200/303, rowcount>0 in-memory) while the write is not yet durable, and a separate process (the CLI, or the server restarting/crashing) would not see it. CONDITION: Development must commit inside decide_approval() itself, and QA must verify durability by reading the row from a second, independent connection immediately after the POST returns, not just trust the HTTP response.
• Unspecified implementation detail Development must not improvise: how the per-run token reaches the <form> hidden field in inbox.html. Proposal claims build_*_html() functions are reused unchanged ('zero duplicate rendering logic') between server.py and the static generator, but the static generate_inbox.py snapshot has no server/token to embed, while the live server page must embed a real one. CONDITION: pin down before implementation whether build_inbox_html() takes an optional token parameter (preferred, still one function) or server.py post-processes the returned string -- do not leave this to be improvised mid-implementation since it is the crux of the write-gate mechanism.
• Server-side input validation gaps not explicitly stated: the POST handler must independently re-validate the decision field against the exact 3-value allowlist (approve/reject/discuss) before calling decide_approval(), so a malformed field produces a clean 400 rather than an uncaught sqlite3.IntegrityError/500 leaking a traceback; the approval_id path segment must be validated as an integer before use. CONDITION: QA test malformed POSTs (bad decision value, non-numeric id, missing token) and confirm clean error responses, not tracebacks.
• New attack-surface note (not a blocker, just needs QA coverage): GET routes like /agents/<name>.html now execute a live parameterized query against attacker-influenceable URL input per request, rather than only ever serving pre-generated static files as in 2A. Loopback-only limits who can reach it, but QA should confirm the existing generator functions use parameterized queries (no string-built SQL) for any URL-derived lookup key, since this is the first time that code path is reachable dynamically instead of only at generation time.
• Minor accuracy issue, not blocking: the claim 'the exact kind of thing this project's Red Team has rejected before' (re: not forcing Founder actions into agent_activity) is not substantiated by any file in ops/reviews -- no prior review contains that finding. The underlying reasoning is sound on its own merits (agent_activity.agent_id is NOT NULL REFERENCES agents(id), so this literally cannot be done without a schema change or a fake agent identity) and I agree with the decision not to write into agent_activity -- just correct or remove the false precedent citation in the final write-up.
• State machine (Q3 in proposal): pending->{approve,reject,discuss}, discuss->{approve,reject}, discuss->discuss rejected, approve/reject terminal, is correct and matches the Founder's brief; enforcement is properly server-side via the atomic UPDATE regardless of what the UI shows/hides, which is the right defense-in-depth (a forged POST re-clicking Discuss or Approve on a resolved/already-discussed row is rejected the same way a UI click would be). No orphan/FK risk: approvals.task_id has FK enforcement (PRAGMA foreign_keys=ON) and task purge already blocks on any approvals row, so a task cannot be deleted out from under a pending approval. Minor gap only: nothing ties a pending approval's fate to its parent task's status changing underneath it (e.g., task independently marked done/cancelled elsewhere) -- worth a one-line note in DATA_MODEL.md but not a blocker for 2B1.
• decide_approval() as the sole writer of approvals.decision, reused by both the CLI wrapper and server.py, is the correct way to honor 'opsdb.py is the only writer' -- not a second writer. No mechanical enforcement exists to stop a future code path from doing a raw UPDATE approvals SET decision=... elsewhere, but that's consistent with how this codebase already documents (not lints) analogous rules elsewhere (e.g. orchestrator-only task-status writes) -- acceptable precedent, not a new gap introduced by this proposal.
