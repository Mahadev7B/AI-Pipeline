# DECISIONS.md — Decision Log

Append-only. Never silently reverse a prior decision — if an agent believes
an existing decision should change, it proposes a **new** decision entry
and runs it through review; the old entry stays as-is for history.

From Phase 1 onward, this file is the git-readable mirror of the `decisions`
table in the operational SQLite database (see `DATA_MODEL.md`) — SQLite is
the writable source of truth, this file is the durable, diffable export.

## Format

```
### DEC-<NNN> — <short title>
Date: <YYYY-MM-DD>
Problem: <what needed deciding>
Options considered: <list>
Decision: <what was chosen>
Reason: <why>
Tradeoffs: <what was given up>
Agent recommending it: <agent name>
Founder approval: <required/not required — and outcome if resolved>
```

### DEC-006 — Milestone 2B4: Founder authentication mechanism selection
Date: 2026-08-30
Problem: The session-token mechanism (Milestone 2B1 onward) proves a request came from a page this server process rendered, but does not prove a human, specifically the Founder, sent it — `risks.id=2`, open since Phase 1. This milestone had to materially close that gap for the current local/internal, solo-Founder, loopback-only Control Center deployment, without adding a paid identity provider, external cloud infrastructure, or any third-party dependency unless the threat model genuinely required it (Security and Red Team both confirmed it did not).
Options considered: Auth0/Clerk/Firebase/OAuth/enterprise IAM (rejected — disproportionate cost/dependency for a single local trusted operator's own machine; would require separate Founder approval for external cost/dependency anyway); an environment-variable passphrase (rejected — leaks via shell history and `/proc/<pid>/environ`, worse exposure than the alternative, and forces re-entry every process start with no session UX); a single Founder passphrase, `hashlib.scrypt`-hashed, credential stored outside git in a 0600 file bootstrapped via a new stdlib-only CLI, gated by a server-side session cookie layered onto the existing centralized `do_POST()`/`do_GET()` check (adopted).
Decision: Implemented `ops/control-center/founder_auth.py` (`scrypt` N=2**17/r=8/p=1, 16+ character passphrase floor, atomic 0600 credential file outside git, never touching `operations.sqlite3`) plus a Founder-session cookie (`HttpOnly`, `SameSite=Strict`, 30-minute idle / 12-hour absolute timeout, in-memory only, wiped on restart) gating all 9 write/auth routes and every GET read at the same centralized location the pre-existing CSRF `SESSION_TOKEN` check already occupied — kept, not replaced. Fully serialized `/api/login` verification closes both the stated brute-force attempt cap and a concurrent-`scrypt` memory-exhaustion DoS, independently verified three separate times under adversarial conditions (Code Review's 60-simultaneous reproduction, Security's 45,820-request/40-second sustained flood) — all PASS.
Reason: The smallest credible mechanism for the actual deployment model — a solo Founder's own local internal tool, not a public SaaS product — that genuinely answers "does the entity submitting this request know a secret only the Founder was ever told," backed by a real, independently-reproduced technical guarantee rather than a documented convention.
Tradeoffs: Does not and structurally cannot defend against an agent with Bash tool access sharing the Founder's own OS-user filesystem/process principal (`risks.id=3`, explicitly out of scope this milestone) — such an agent can read or overwrite the credential file directly, run `founder_auth.py` itself, or `PTRACE_ATTACH` the running server process and read session state out of memory. Also disclosed: the shared, non-identity-scoped lockout can itself be flooded by an actor already inside this design's own threat class to deny the Founder's own genuine logins (Red Team's Milestone 2B4 finding F1) — no cheap in-scope fix exists without touching `risks.id=3`. Neither gap is hidden; `risks.id=2` moves to `mitigated`, deliberately not `resolved`.
Agent recommending it: CTO (see `ops/reviews/cto-milestone2b4-architecture.md`), Security threat model (`ops/reviews/security-milestone2b4-threat-model.md`), Red Team (`ops/reviews/red-team-milestone2b4-architecture.md`).
Founder approval: **APPROVED 2026-08-30 (Founder directive, Part B — Milestone 2B4).** TASK-013, all gates PASS/CONFORMS — see `ops/reviews/code-review-milestone2b4.md`, `ops/reviews/qa-milestone2b4.md`, `ops/reviews/security-adversarial-milestone2b4.md`, `ops/reviews/cto-milestone2b4-conformance.md`. Recorded as decision id=9 in the operational database. `risks.id=2` moved `open` → `mitigated` — see `ops/db/opsdb.py query "SELECT * FROM risks WHERE id=2"`.

### DEC-007 — Phase 3A: zero-tool automated Code Review + in-process background poller, not native tool grants or a second process
Date: 2026-08-31
Problem: The Founder authorized Phase 3A — a Chief of Staff Founder conversational interface, plus one narrowly-scoped autonomous handoff (Developer complete → Code Review) — explicitly requiring the system to "recognize completion automatically" and route a completed Developer handoff to Code Review without a human click, while explicitly refusing to authorize full Phase 3 automation, refusing to claim `risks.id=3` (Bash tool access cannot be scoped below the tool-category level) was solved, and requiring the Security threat model to specifically examine how autonomous operation changes that risk's practical consequence.
Options considered: Real Bash/filesystem tool grants for an unsupervised automated Code Review invocation, so it could genuinely explore the repository the way a human-supervised review session can (rejected — would be the first unattended-Bash precedent in this system's history, under the identical already-open, already-flagged OS-user principal `risks.id=3` names); a standalone second process/script polling the database for eligible tasks (rejected — adds an operational surface the Founder would have to separately remember to run, monitor, and stop, contradicting this system's deliberate one-process design); zero-tool invocation (`--tools ""`, `--strict-mcp-config`, unconditional — identical to every invocation this system has ever made) with deterministic Python assembling a real transcript — task metadata, the Developer's handoff record, a real `git diff` between validated commit SHAs, full file content retrieved via `git show <sha>:<path>` (the git object database, never a live filesystem read), and `CODING_STANDARDS.md` — plus an in-process `daemon=True` polling thread living inside `server.py`'s own existing process (adopted).
Decision: Implemented exactly as adopted. `AUTOMATED_REVIEW_ALLOWLIST` invokes `code-review` with the same unconditional zero-tool flags every other invocation in this codebase has always used — verified to have zero diff across `agent_runtime.py`'s `_run_claude()` for this entire milestone, independently re-confirmed by Code Review, Security's adversarial review, and CTO's post-implementation conformance. `automation.py`'s poll loop (`POLL_INTERVAL_S=20`) lives inside `server.py`'s existing process, started/stopped alongside it, gated by a default-disabled kill switch (`automation_state.enabled`) only the Founder can flip via two new CSRF+session-gated routes. New `automation_events` table's `UNIQUE` constraint on the triggering `task_status_history` row is the real, DB-enforced idempotency guarantee (confirmed under 20 real concurrent claim attempts — exactly one succeeded). A `PASS` leaves `tasks.status` unchanged at `CODE_REVIEW` (no automatic advance to `QA`); a `REJECT` performs a single mechanical `CODE_REVIEW → IN_DEVELOPMENT` status rollback, never a new Developer invocation — both per the Founder's explicit, narrow authorization. Part A of the same milestone shipped the Chief of Staff's own real conversational interface (`POST /api/chief-of-staff/ask`, the first-ever real `claude --agent orchestrator` invocation in this system's history, also zero-tool, also gated by the same auth boundary), reusing the existing Executive Meeting machinery for "ask other agents what they think" rather than inventing a second orchestration system.
Reason: Every existing invocation in this codebase has been deliberately, consistently restricted to zero tools specifically because no human is watching a given call in real time — that reasoning applies with equal or greater force to an invocation not even triggered by a Founder action, but by a background poller noticing database state on its own. A single existing process, extended with a daemon thread, is the smallest addition that satisfies "the system recognizes completion automatically" without adding a second operational surface the Founder would have to separately manage.
Tradeoffs: Does not resolve, narrow, or reduce `risks.id=3` — its practical consequence genuinely increases in two independently additive ways, disclosed in full rather than hidden: (1) a same-OS-user actor no longer needs to forge an authenticated HTTP request to get a real, costed model invocation to run — writing a plausible `CODE_REVIEW` transition and handoff via `opsdb.py` directly (already possible before this milestone) is now sufficient, since the poller acts unattended on its own cycle; (2) the Python code assembling diff/file content now walks real filesystem paths and shells out to `git` based on database content the same actor already controls — mitigated (path-traversal validation including symlink resolution, commit-SHA format/existence validation, fixed argv with `--` separators, git-object-database content retrieval) but not eliminated as a new surface. Automated Code Review structurally cannot catch cross-file consistency/duplication defects a human-supervised session could (disclosed in the automated mode's own persona note). Both gaps were adversarially re-verified, not merely asserted: Security's adversarial review reproduced the full same-OS-user attack end-to-end and confirmed its blast radius is exactly as bounded as documented (one zero-tool invocation, ~$0.08 real cost), and ran live prompt-injection attempts against both new invocation types — both were explicitly detected and refused by the model itself.
Agent recommending it: CTO (see `ops/reviews/cto-phase3a-architecture.md`), Security threat model (`ops/reviews/security-phase3a-threat-model.md`), Red Team (`ops/reviews/red-team-phase3a-architecture.md`).
Founder approval: **APPROVED 2026-08-31 (Founder directive, "PHASE 3A: LIMITED AUTOMATION + CHIEF OF STAFF FOUNDER INTERFACE").** TASK-015, all gates PASS/CONFORMS across two Development passes (Part A, then Part B, per Red Team's recommendation) — see `ops/reviews/code-review-phase3a-parta.md`, `ops/reviews/code-review-phase3a-partb.md`, `ops/reviews/qa-phase3a.md` (the Founder's own 12-point acceptance test demonstrated end-to-end with real, unmocked model invocations), `ops/reviews/security-adversarial-phase3a.md`, `ops/reviews/cto-phase3a-conformance.md`. Recorded as decision id=10 in the operational database. `risks.id=3` remains `open`, `mitigation` text updated to reflect the two-part consequence increase — see `ops/db/opsdb.py query "SELECT * FROM risks WHERE id=3"`. Full Phase 3 automation (automatic Code Review PASS → QA, QA → Security, Security → Release, and production deployment) remains explicitly unauthorized.
