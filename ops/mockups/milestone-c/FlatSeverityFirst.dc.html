Mitigation
CTO investigation of QA's TASK-017 live-reproduced finding (qa_results.id=70) complete: ops/reviews/cto-risk3-hook-invocation-investigation.md. Confirmed directly against the installed Claude Code CLI binary (v2.1.252): PreToolUse hooks registered in a subagent's own frontmatter (.claude/agents/developer.md) are silently skipped by the harness whenever the folder is not marked "trusted" -- confirmed true for this live repo's own persisted trust state, in every non-interactive invocation this project's actual deployment pattern uses. A REAL non-interactive fix exists (harness-native, found directly in CLI source): set projects["<repo-path>"].hasTrustDialogAccepted: true in the global config file ($CLAUDE_CONFIG_DIR/.claude.json or ~/.claude.json) as a one-time deployment step before any agent session runs -- not a publicly documented CLI flag, but a real mechanism the harness's own error text names. HOWEVER this fix does NOT hold up adversarially: that trust flag lives in a file entirely outside the repo, writable by the same OS user every agent (including Developer) runs as, with zero coverage in the hook's own denylist -- a Developer-role Bash command can silently revert it in one unobfuscated line, with zero audit trail, disabling the entire hook mechanism for every future session at once (a stronger, more complete self-undo than any single previously-disclosed bypass). This means the Chief of Staff synthesis's "reduced, not closed" verdict was premature specifically for the Developer-denylist half of the reduction: it delivers zero protection today, and even after the invocation-context fix ships, it would only ever be a soft, non-adversarial-scope speed bump, self-revertible by the very role it targets -- not the "harness-enforced narrowing Developer itself cannot quietly undo" the synthesis claimed. The reviewer zero-tool rollout (Code Review/Security/Red Team's synchronous routes) is unaffected by any of this -- it uses --tools "" unconditionally, independent of workspace trust/hooks entirely -- and remains the one durable, delivered reduction from this milestone, confirmed working by QA. Two secondary hook bugs (leading-space substring boundary bug on " gdb"/" strace"; shlex.split() quadratic-time hang-to-fail-open near the harness's 600s hook timeout) are real, cheap, and recommended for fixing regardless, as defense in depth. risks.id=3 stays open, not "mitigated" -- whether to accept the Developer-denylist's narrowed (non-adversarial-only) scope explicitly, or revisit OS-level/sandboxing separation (previously rejected as disproportionate, before this ceiling was known), is a Founder-level tradeoff this investigation surfaces but does not resolve. Recommendation now goes to Security/Red Team before Development resumes, per the Founder's standing gate sequence.

Mitigation
Founder-facing actions -- all 9 write/auth routes (/api/login, /api/logout, and the 7 pre-existing write routes) and every GET read -- require a locally authenticated Founder session: a 16+ character passphrase known only to the Founder, verified via a salted hashlib.scrypt hash (N=2**17, r=8, p=1) stored outside git (ops/control-center/.founder_credential.json, 0600, atomic writes, never touching operations.sqlite3, logs, or generated HTML), gated by a server-side session cookie (HttpOnly, SameSite=Strict, 30-minute idle / 12-hour absolute timeout, in-memory only, wiped on restart), and rate-limited against brute force via fully serialized login verification (closes both the stated 5-attempt cap and a concurrent-scrypt memory-exhaustion DoS -- independently verified under a 60-simultaneous and a 45,820-request sustained flood). This closes the gap for any local actor that does not already share the Founder's own OS-user filesystem/process principal -- a real, previously-open gap, now shipped and independently verified three times (Code Review, QA, Security post-implementation adversarial pass, all PASS). It does NOT close the case where an agent runs with Bash tool access under the Founder's own OS user (risk id=3): such an agent can read or overwrite the credential file directly, run founder_auth.py itself, or PTRACE_ATTACH the running server process and read session state out of memory -- exactly as it could already read a served page's CSRF token before this milestone. Also disclosed and unresolved: the shared, non-identity-scoped lockout can be flooded by an actor already inside this design's own threat class to deny the Founder's own genuine logins (Red Team's Milestone 2B4 finding F1) -- no cheap in-scope fix exists without touching risk id=3. Closing either gap requires resolving risk id=3 first, or a different class of infrastructure this milestone's scope deliberately excludes. See ops/reviews/cto-milestone2b4-architecture.md, ops/reviews/security-milestone2b4-threat-model.md, ops/reviews/red-team-milestone2b4-architecture.md, ops/reviews/code-review-milestone2b4.md, ops/reviews/qa-milestone2b4.md, ops/reviews/security-adversarial-milestone2b4.md, ops/reviews/cto-milestone2b4-conformance.md.

low resolved
