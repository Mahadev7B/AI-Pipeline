The Start action — arm, confirm, after-state, failure

The Start action — every state

Start is the first control in this product that begins a multi-stage pipeline on a click. These are its four states, the two-step shape that separates it from Save, and the honest failure case. Real content throughout: TASK-025 as it exists in the database today.

1. Why Save and Start cannot look alike

The palette is already fully spoken for — amber = active / primary, green = passed, red = danger & open risk, blue = agent waiting, violet = actor identity, gray = neutral. Inventing a sixth colour for “expensive” would break a closed system; painting Start red would lie about it (starting work is the thing the Founder is supposed to do). So the two actions are separated by fill, step count and label, not by hue.

No fill, and an ellipsis: in this UI an unfilled button has never been the “go”. Clicking it dispatches nothing — it opens step 2.

The filled button appears exactly once, on a screen whose entire body is the consequence disclosure. Its label names the agent and the spend — it can’t be misread as “save”.

2. Step 2 — the confirmation screen

Server-rendered, not a browser confirm() — this product renders every state on the server and runs no client JS. The Founder’s idea is repeated back on this screen, so “which idea am I about to spend money on” is never a question.

3. After-state — “started” must be as unmistakable as “saved”

The mirror image of the save confirmation: it names what is running, where to watch it, and it removes the Start control entirely — a second click is impossible, not merely discouraged. Same in-progress lock the Ask-Agent panel already uses.

4. Failure — the state this project has already got wrong once

TASK-023 shipped a sandbox that reported success while doing nothing, and QA caught it. The Start path is the same shape of risk: a dispatch that fails must never render the “Started” panel. If the pipeline was not dispatched, the screen says so in those words and the task is still in the Backlog.
Start failed
Not started. TASK-025 is still in the Backlog.
The dispatch did not go through, so no agent was started and nothing was spent. The idea is untouched and its status is still BACKLOG — you can try again, and trying again starts one pipeline, not two.
The word “started” never appears unless a status change was actually written.
Try starting it again…
Already running — the double-click lock
Product is already working on this.
Reached by a refresh, a back-button, or a second tab. No Start control is rendered and the route refuses a second dispatch — the same in-progress lock the Ask-Agent panel already uses (“a request is already in progress”), applied to a far more expensive action.
Save is idempotent-ish and cheap; Start is neither. It gets the stricter guard.
